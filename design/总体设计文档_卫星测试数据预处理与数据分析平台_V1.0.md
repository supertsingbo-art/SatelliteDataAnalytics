# 卫星测试数据预处理与数据分析平台
## 总体设计文档（V1.1）

## 1. 文档目的与范围
本文档用于定义平台总体设计方案，覆盖技术架构、业务架构、数据架构与部署架构，作为研发实施、测试验收和运维交付依据。

适用范围：
- 卫星测试历史数据预处理与一致性比对业务；
- 一期建设范围（模板配置、数据预处理、算法处理、比对分析、报告输出）；
- 后续机器学习扩展的预留设计。

## 2. 设计原则
- 分层解耦：业务规则、计算执行、存储访问解耦；
- 可追溯：全链路记录模板版本、任务批次、时间窗、输入输出血缘；
- 可扩展：模板化规则、插件化算法、对象存储可替换；
- 可运维：可观测、可重试、可回补、可灰度发布；
- 安全可控：RBAC 权限、代码执行隔离、审计日志完整。

## 3. 总体架构概览
系统采用“Web 管理端 + .NET 业务后端 + 任务调度与工作节点 + 多存储分层”架构。

核心链路：
1. 用户配置模板（筛选/算法/报告）并发布；
2. Hangfire 触发任务（定时或手工补跑/重跑/回补）；
3. 预处理引擎从 MongoDB 拉取原始数据并按规则过滤；
4. 高品质数据写入 ClickHouse (Upsert)，并将溯源元数据写入 PostgreSQL；
5. 算法引擎解析 React Flow 的算法编排，执行从统计到聚类等多阶分析处理并生成结果；
6. 比对引擎输出一致性结论；
7. 报告引擎生成 Word 文档并存入 MinIO；
8. 平台提供任务监控、结果查询和审计追踪。

## 4. 技术架构

### 4.1 技术选型
- 后端框架：C# / .NET 8（ASP.NET Core Web API）
- 前端框架：**React + TypeScript + React Flow**（用于大模型工作流风格的算法拖拽编排）
- 调度组件：Hangfire
- 原始数据源：MongoDB（长表）
- 分析存储：ClickHouse
- 元数据存储：PostgreSQL（建议）
- 对象存储：MinIO（兼容 S3 替代品）
- 缓存/锁：Redis（建议）
- 可观测：日志 + 指标 + 告警（OpenTelemetry 体系可选）

### 4.2 应用分层
- 接入层（API Layer）
  - 统一认证授权（JWT + RBAC）
  - 接口网关与参数校验
- 应用层（Application Layer）
  - 模板服务、任务服务、报告服务、比对服务
- 领域层（Domain Layer）
  - 规则模型、任务状态机、审计模型、版本模型
- 基础设施层（Infrastructure Layer）
  - Mongo/ClickHouse/PostgreSQL/MinIO/Hangfire 适配器

### 4.3 核心模块
- TemplateService：模板管理、版本、启停、灰度发布
- TaskOrchestrator：任务编排、状态推进、重试与幂等
- PreprocessEngine：有效段计算、离群判定、质量标记、入仓
- AlgorithmEngine：内置算法执行（预留插件扩展）
- CompareEngine：同星跨批次 + 实测与阈值比对
- ReportEngine：Word 模板渲染、文件入 MinIO
- AuditService：全链路操作与血缘记录
- IntegrationService（可选）：第三方开放 API、异步任务、Webhook 出站投递

### 4.4 对外集成架构（HTTPS REST，可选模块）
- **协议**：第三方默认使用 **HTTPS + REST + JSON**（OpenAPI 描述）；
- **同步查询**：任务元数据、算法汇总指标、结果摘要；
- **异步长任务**：`POST` 创建任务 → **202 Accepted** + `jobId`/`runId` → 第三方 **轮询** `GET /jobs/{id}`；
- **完成通知**：任务完成后由本系统 **HTTP POST** 至第三方 **callbackUrl**（Webhook），正文含状态与结果/下载链接；**HMAC 签名**、**eventId 幂等**、失败 **重试** 与 **callback_deliveries** 表审计；
- **鉴权**：API Key（哈希存储）或 OAuth2 Client Credentials 等；
- gRPC 可作为与特定伙伴的**可选**增强，不作为第三方默认接口。

### 4.5 任务执行架构（Hangfire 角色边界）
- Hangfire 负责：任务触发、排队、重试、监控；
- Worker/业务服务负责：实际计算和数据处理；
- 超时策略：单任务上限 8 小时，超时中断并记录失败原因；
- 队列隔离建议：preprocess / algorithm / compare / report。

### 4.6 安全架构
- 身份认证：JWT
- 权限模型：管理员、分析员、只读员
- 数据访问控制：按角色 + 业务范围
- 上传算法安全：容器级隔离、资源限制、审计追踪（一期可预留）
- 审计要求：关键操作留痕，不可篡改（通过审计库与备份保障）

## 5. 业务架构

### 5.1 业务能力地图
- 资产配置中心
  - 数据源管理
  - 卫星资产字典
  - 参数字典映射（逻辑别名与物理ID映射）
- 模板中心
  - 筛选模板
  - 算法模板
  - 报告模板
- 任务中心
  - 定时任务
  - 手工补跑/重跑/回补
  - 执行监控
- 数据处理中心
  - 预处理与质量标记
  - 算法处理
  - 一致性比对
- 报告中心
  - 报告生成
  - 报告归档
  - 报告查询与下载
- 治理中心
  - 灰度发布
  - 审计追踪
  - 运维告警
- 开放集成中心（可选）
  - API 客户端与凭据
  - 异步任务与 Webhook 回调

### 5.2 关键业务流程
#### 流程A：模板发布流程
1. 用户创建模板；
2. 保存为新版本；
3. 审核/启用；
4. 灰度规则生效（卫星/批次/时间窗）。

#### 流程B：预处理任务流程
1. 触发任务（定时或手工），指定目标卫星与批次；
2. 引擎解析模板，通过参数字典映射将逻辑别名实时转换为底层物理 ID；
3. 从 Mongo 根据物理 ID 查询原始数据；
4. 计算有效时间段；
4. 提取目标参数；
5. 判定离群值并标记；
6. 测点数值写入 ClickHouse 高品质明细表（Upsert），同步将任务血缘与规则写入 PostgreSQL 时间窗元数据表；
7. 写入任务审计与血缘信息。

#### 流程C：分析与报告流程
1. 算法引擎解析 React Flow 生成的 DAG 图，按节点执行算法模板（支持统计、频域、聚类、时序对齐等五阶算法）；
2. 执行一致性比对（多维基线比对、形态对齐等）；
3. 汇总结果；
4. 按报告模板生成 Word；
5. 入 MinIO 并回写索引；
6. 前端展示与下载。

#### 流程D：第三方异步查询与回调（可选）
1. 第三方携带鉴权调用开放 API 创建异步任务（或查询已有 `run_id`）；
2. 返回 202 与任务标识；
3. 第三方轮询直至终态，或注册 callbackUrl 接收 Webhook；
4. 本系统任务完成后 POST 回调，失败重试并记录投递日志。

### 5.3 业务规则摘要
- 筛选规则：AND/OR/NOT，支持持续时长、边界缓冲；
- 数据质量：不插值、不去重；
- 离群策略：支持上下限、常用统计法，支持全局/分段判定；
- 离群值入库：不剔除，标记保存；
- 报告规范：多模板可编辑，封面/章节/页码必需。

## 6. 数据架构

### 6.1 数据分层
- ODS（原始层）
  - 存储：MongoDB
  - 内容：原始长表参数数据
- DWD（高品质明细层）
  - 存储：ClickHouse
  - 内容：过滤后参数明细 + 质量标记
- DWS（汇总分析层）
  - 存储：ClickHouse
  - 内容：算法结果、比对结果
- META（元数据层）
  - 存储：PostgreSQL
  - 内容：模板、版本、任务、审计、血缘、配置
- FILE（对象层）
  - 存储：MinIO/S3
  - 内容：报告文件、算法包、导出附件

### 6.2 核心数据实体（逻辑）
- raw_param_point（Mongo）
  - satellite_id, test_batch_id, param_id, ts, value, unit, description
- hq_param_point（ClickHouse，极简明细表）
  - 业务联合主键：`satellite_id, test_batch_id, param_id, ts`
  - 数值状态：`raw_value, processed_value, is_outlier`
  - 说明：同一 `(satellite, batch, param, ts)` 在 ClickHouse 中**仅保留最新的一份**（Upsert语义）。取消行级 `run_id` 和冗长模板信息。
- hq_param_metadata（PostgreSQL，时间段元数据）
  - `satellite_id, test_batch_id, param_id, window_start, window_end`
  - `run_id, template_version, outlier_method, outlier_reason_pattern`
  - 说明：抽取时间段维度的元数据，记录某段时间内的参数数据是由哪次任务、哪个模板处理的，以及异常判定的依据。前端或下游可通过时间范围关联该表获取数据血缘与详细判定规则。
- algo_result（ClickHouse）
  - run_id, template_version, metric_name, metric_value, window_start, window_end
  - **聚类扩展**：对于无监督聚类算法，此表可额外记录聚类簇分布特征、簇漂移量（Centroid Drift）等宏观统计指标。
- algo_cluster_labels（ClickHouse，新增）
  - `satellite_id, test_batch_id, ts, cluster_id`
  - 记录每个时间戳样本所属的聚类工况（伪标签）及孤立点/离群值标记（如标签 -1）。
- compare_result（ClickHouse）
  - compare_run_id, compare_type, baseline_ref, score, decision, detail_json
- template_meta（PostgreSQL）
  - template_id, template_type, version, status, gray_scope, config_json
- task_run（PostgreSQL）
  - run_id, job_type, trigger_type, status, start_time, end_time, timeout_flag, error_msg
- audit_log（PostgreSQL）
  - operator, action, target_id, before_json, after_json, action_time
- object_index（PostgreSQL）
  - object_id, bucket, object_key, version, checksum, content_type, ref_run_id
- api_clients / client_callbacks / callback_deliveries（PostgreSQL，可选）
  - 第三方客户端、回调 URL、签名密钥版本、Webhook 投递记录

**PostgreSQL 表级展开**（用户、角色、模板主表与版本、灰度规则、`job_runs`、审计、`stored_objects`、API 与回调等）见《PostgreSQL元数据与对外接口设计说明_V1.0.md》。

### 6.3 数据血缘与可追溯
每个结果记录必须可追溯：
- 来源任务 run_id；
- 模板版本 template_version；
- 输入数据时间窗；
- 数据来源批次（satellite_id + test_batch_id）；
- 输出文件 object_id（如报告）。

### 6.4 数据保留与归档建议
- **单表+分区设计**：高品质明细表（hq_param_point）采用“单张大表”设计，通过 `PARTITION BY (toYYYYMM(ts), satellite_id)` 实现按月与按星的物理分区隔离。保证跨星联合分析性能的同时，简化数据归档与销毁（可直接 `DROP PARTITION`）；
- 历史冷数据可利用 ClickHouse 存储策略下沉归档；
- 审计数据长期保留；
- MinIO 开启版本控制与生命周期策略。

### 6.5 机器学习 / 深度学习（序列）与库表关系
- **ClickHouse**：时序点与聚合指标的事实存储；
- **ML 样本**：序列/深度学习所需 `[T,C]`、mask、标签等，在 **ML 数据集快照或导出层** 定义，与 HQ 层解耦；
- **版本**：数据集快照 ID、`run_id` 集合、通道映射、归一化参数文件（可存 MinIO）需在元数据（PostgreSQL）登记；
- **防泄漏**：划分优先按批次/时间；特征窗口不包含未来标签信息。

## 7. 部署架构

### 7.1 部署拓扑（逻辑）
- 接入区
  - Web 前端
  - API 服务（可多实例）
- 计算区
  - Hangfire Server（任务调度）
  - 预处理 Worker
  - 算法 Worker
  - 比对 Worker
  - 报告 Worker
- 数据区
  - MongoDB
  - ClickHouse
  - PostgreSQL
  - MinIO
  - Redis（可选）

### 7.2 环境规划
- DEV：单机或轻量多容器
- SIT/UAT：接近生产，验证联调和性能
- PROD：多实例高可用，数据备份与监控完善

### 7.3 高可用与容灾建议
- API 与 Worker 多副本部署；
- 任务队列与数据库定期备份；
- ClickHouse 与对象存储具备冗余策略；
- 关键配置与模板版本异地备份。

### 7.4 运维与监控
- 监控维度：
  - 任务成功率、失败率、超时率
  - 队列积压长度
  - Mongo 查询时延
  - ClickHouse 写入/查询耗时
  - 报告生成耗时
- 告警规则：
  - 连续失败任务
  - 超时任务
  - 回补积压
  - 存储容量阈值

## 8. 非功能设计

### 8.1 性能
- 支持批处理高吞吐写入 ClickHouse；
- 任务并发可配置，避免资源争抢；
- 长任务分片执行，降低单任务失败影响面。

### 8.2 可靠性
- 任务幂等：按模板版本 + 时间窗 + 批次生成幂等键；
- 失败可重试，可人工重跑；
- 回补可按窗口精确触发。

### 8.3 可维护性
- 模块边界清晰；
- 配置集中管理；
- 关键流程具备审计与可观测信息。

### 8.4 安全性
- RBAC 权限控制；
- 重要数据最小权限访问；
- 上传代码执行隔离与审计（扩展能力）。

## 9. 分阶段实施建议

### 一期（当前）
- 打通业务闭环：模板 -> 预处理 -> 算法 -> 比对 -> 报告；
- 完成任务治理与审计可追溯；
- 上线基础运维能力。

### 二期（演进）
- 增强可视化编排（复杂分支/循环/并行）；
- 完善插件化算法运行时；
- 增加 ML 数据集版本化与特征工厂能力。

---

## 10. 风险与对策
- 规则频繁变化：模板版本治理 + 周评审冻结窗口；
- 长任务超时：队列隔离 + 分片执行 + 超时中断；
- 跨库一致性：状态机 + 幂等键 + 补偿机制；
- 报告模板复杂：模板规范与渲染校验器；
- 性能瓶颈：基准压测先行，分区与索引策略优化。

## 11. 结论
本方案满足当前业务目标与治理要求，具备工程可落地性与后续扩展空间。建议按一期范围先行实施，优先交付可追溯、可重跑、可出报告的稳定闭环能力。
