# 卫星测试数据预处理与数据分析平台
## 概要设计文档（V1.0）

## 1. 引言

### 1.1 编写目的
本文档基于《需求分析说明文档_V1.9》与《总体设计文档_V1.7》，对“卫星测试数据预处理与数据分析平台”的系统架构、功能模块、数据结构及接口设计进行概要抽象。本文档将作为后续详细设计与开发落地的核心指导手册，确保技术方案100%覆盖最新演进的业务需求。

### 1.2 核心业务目标
将海量卫星测试原始数据（MongoDB）经过模板化规则过滤、离群值判定后，沉淀为高品质数据资产（ClickHouse）；通过工作流式拖拽编排，执行从基础统计到多维聚类的高阶算法分析，完成同星跨批次与实测基线的一致性比对，最终输出标准化Word报告，并为后续机器学习（ML/DL）提供纯净的时序事实与伪标签。

---

## 2. 总体架构设计

### 2.1 技术选型
- **前端展现层**：React + TypeScript + **React Flow**（支撑大模型工作流风格的拖拽式算法节点编排，左侧组件、中间连线画布、右侧属性配置）。
- **后端服务层**：C# / .NET 8 LTS (ASP.NET Core Web API)，提供标准 RESTful 服务。
- **任务调度与异步执行**：Hangfire（负责超时控制、重跑、回补与可视化监控）。
- **数据存储层**：
  - **原始数据**：MongoDB（贴源长表数据）。
  - **分析数据库**：ClickHouse（高吞吐、海量时序点与聚合指标存取）。
  - **元数据与血缘**：PostgreSQL（模板、任务溯源、API 客户端及 Webhook 投递记录）。
  - **对象存储**：MinIO（兼容 S3，用于报告、算法包与导出文件）。

### 2.2 逻辑架构分层
系统采用经典的分层解耦设计：
1. **API 网关/接入层**：统一鉴权（JWT/API Key），REST API 暴露。
2. **业务流程层**：模板发布流水线、长任务异步状态机。
3. **计算引擎层**（核心）：
   - **预处理引擎**：求有效时间段、提取参数、进行阈值/3-Sigma离群判定。
   - **算法执行引擎**：解析 React Flow 生成的 DAG 图，按节点依赖流转参数，支持五阶算法体系。
   - **比对引擎**：将算法产物与基线/历史进行对比打分。
   - **报告引擎**：Word 模板装配与对象存储落盘。
4. **数据存储隔离层**：屏蔽底层 Mongo/ClickHouse/PG 的读写差异，实现“高品质明细与元数据拆分”的双写逻辑。

## 3. 核心功能模块设计（覆盖需求演进）

### 3.1 资产字典与模板编排中心
- **参数字典映射与逻辑解耦**：引入参数字典与映射机制，模板配置时仅使用“逻辑别名”，在任务调度流转时由引擎动态解析为底层数据库的物理 ID。彻底解决 100 颗卫星跨星组网时的硬件 ID 差异，实现模板的高度复用。
- **筛选模板管理**：配置 AND/OR/NOT 逻辑、持续时长、边界缓冲。
- **算法工作流编排（重点）**：引入 React Flow。将统计算法、频域处理（FFT）、时序对齐（DTW）、无监督聚类（DBSCAN/K-Means）封装为标准化节点。实现并行、分支、循环及参数透传的连线校验。

### 3.2 高品质数据构建链路
贯彻**“不插值、不去重”**原则：
- 支持定时抽取与晚到数据自动回补。
- **离群值双态保留**：被判定异常的数据打上标记继续入库，绝不物理删除。

### 3.3 算法与一致性比对（五阶演进能力落地）
引擎必须支持并预留以下五阶算法能力接口：
1. **稳态与规则**：统计聚合与上下限包络比对。
2. **频域扩展**：针对振动/微波的高频数据 FFT / PSD 比对。
3. **时序形态对齐**：针对非稳态指令响应动作的 DTW 瞬态打分。
4. **多维基线与聚类**：降维与无监督聚类，切分工况、生成伪标签并计算簇中心漂移（Centroid Drift）。
5. **预测重构**：预留自编码器（AE）深度学习模型的重构误差比对接口。

## 4. 数据架构设计（核心重构）

针对 100 颗卫星 × 1.5 万参数的庞大数据量，采用**“极限降维瘦身 + 单表分区”**的设计：

### 4.1 ClickHouse 物理表设计（高吞吐与多维查询）
- **`hq_param_point`（高品质明细表）**：
  - **极简结构**：仅保留联合主键 `(satellite_id, test_batch_id, param_id, ts)`，数值 `raw_value, processed_value` 及 `is_outlier`。
  - **物理分区**：强烈采用 **“单张大表 + `PARTITION BY (toYYYYMM(ts), satellite_id)`”**，彻底规避“一星一表”带来的联合比对灾难。
  - **覆盖重算语义**：采用 `ReplacingMergeTree`，同一参数同时段重跑时，底层自动实现 Upsert。
- **`algo_cluster_labels`（聚类标签表）**：独立记录各个时间戳样本的簇标签与噪声标记，避免修改海量明细表。
- **`algo_result` & `compare_result`**：存储各类统计、特征、频域指标及最终一致性判断结论。

### 4.2 PostgreSQL 溯源元数据层
- **`hq_param_metadata`（时间窗元数据表）**：
  - 承接从 ClickHouse 明细中剥离出来的冗余溯源信息。
  - 记录 `(参数, 时间窗)` 对应的 `run_id`、使用的模板版本、离群判定原因（如 `Threshold [0,100]`）。
  - 前端或第三方查询时，通过时间戳在此表中反查血缘关系。

## 5. 接口与第三方集成设计

### 5.1 异步任务机制（长连接解耦）
预处理和比对任务通常耗时极长（受限于 8 小时强制中断策略），对外 API 采用异步解耦设计：
1. 客户端发起 `POST /api/v1/jobs/preprocess`。
2. 系统立刻返回 `HTTP 202 Accepted` 及全局唯一 `jobId` / `runId`。

### 5.2 状态获取双兜底机制
1. **轮询机制（Pull）**：提供 `GET /api/v1/jobs/{id}` 供第三方定时查询进度与简要结果。
2. **Webhook 回调（Push）**：
   - 第三方在提交任务时可携带 `callbackUrl`。
   - 任务终态（成功或失败）时，系统主动发起 `HTTP POST` 推送。
   - **投递可靠性**：基于 HMAC 签名防篡改，结合事件幂等键（eventId）及退避重试策略。PostgreSQL 中的 `callback_deliveries` 表保存所有投递审计日志。

## 6. 非功能设计与验收约束

### 6.1 性能与可靠性
- **吞吐优化**：MongoDB 到 ClickHouse 的写入必须采用微批处理（Micro-batching，如 10 万条 / 批），严禁单条 Insert。
- **幂等性**：全链路均可基于 `(卫星, 测试批次, 时间窗, 模板版本)` 重新触发。

### 6.2 扩展性与未来 AI 演进
- ClickHouse 数据被视为标准“时序事实”。未来的机器学习张量样本 `[T,C]` 或变长序列将在外部平台上组装并记录快照。
- 保证缺失数据使用 Mask（掩码）表达，严格恪守底层不插值的禁令。

### 6.3 部署架构建议
建议采用容器化混合部署：
- 核心管理 API 及 Hangfire 调度主节点高可用部署。
- 后台 Worker 按计算密集度隔离队列（预处理 Worker 队列、算法聚类 Worker 队列、报告 Worker 队列）。
- 数据库集群化：ClickHouse 搭配 Zookeeper，MinIO 开启多盘纠删码与版本控制。
