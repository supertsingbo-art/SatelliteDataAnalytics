# 卫星测试数据预处理与一致性比对平台
## 概要设计文档（V2.7 合并版）

## 1. 引言

### 1.1 编写目的
本文档由原《总体设计文档 V1.7》与原《概要设计文档 V1.0》合并而成，作为研发实施、测试验收与运维交付的统一技术依据。文档基于《需求分析说明文档 V1.9》编写，覆盖技术架构、业务架构、数据架构、部署架构与非功能设计，确保技术方案 100% 覆盖业务需求。

### 1.2 适用范围
- 卫星测试历史数据预处理与一致性比对业务；
- 一期建设范围：模板配置、数据预处理、算法处理、比对分析、报告输出；
- 后续机器学习扩展的预留设计。

### 1.3 核心业务目标
将海量卫星测试原始数据（MongoDB）经过模板化规则过滤、离群值判定后，沉淀为高品质数据资产（ClickHouse）；通过工作流式拖拽编排，执行从基础统计到多维聚类的高阶算法分析，完成同星跨批次与实测基线的一致性比对，最终输出标准化 Word 报告，并为后续机器学习提供纯净的时序事实与伪标签。

### 1.4 设计原则
- **分层解耦**：业务规则、计算执行、存储访问解耦；
- **可追溯**：全链路记录模板版本、任务批次、时间窗、输入输出血缘；
- **可扩展**：模板化规则、插件化算法、对象存储可替换；
- **可运维**：可观测、可重试、可回补、可灰度发布；
- **安全可控**：RBAC 权限、代码执行隔离、操作留痕日志完整。

## 2. 总体架构

### 2.1 架构概览
系统采用"Web 管理端 + .NET 业务后端 + 任务调度与工作节点 + 多存储分层"架构。

**核心数据链路**：
1. 用户配置模板（筛选/算法/报告）并发布；
2. Hangfire 触发任务（定时或手工补跑/重跑/回补）；
3. 预处理引擎从 MongoDB 拉取原始数据并按规则过滤；
4. 高品质数据写入 ClickHouse（Upsert），溯源元数据写入 PostgreSQL；
5. 算法引擎解析 React Flow 编排，执行从统计到聚类等多阶分析；
6. 比对引擎输出一致性结论；
7. 报告引擎生成 Word 文档并存入 MinIO；
8. 平台提供任务监控、结果查询和操作留痕。

### 2.2 技术选型
| 组件类别 | 技术选型 | 用途说明 |
|---|---|---|
| 前端框架 | React + TypeScript + **React Flow** | 大模型工作流风格的算法拖拽编排 |
| 后端框架 | C# / .NET 8 LTS（ASP.NET Core Web API） | RESTful 服务、模板治理、任务编排 |
| 任务调度 | Hangfire | 定时触发、重试、超时控制、可视化监控 |
| 原始数据源 | MongoDB | 贴源长表数据 |
| 分析存储 | ClickHouse | 海量时序点与聚合指标存取 |
| 元数据存储 | PostgreSQL | 模板、任务、API 客户端、Webhook 投递 |
| 对象存储 | MinIO（兼容 S3） | 报告、算法包、导出附件 |
| 缓存/锁 | Redis（建议） | 分布式锁与短期缓存 |
| 可观测 | OpenTelemetry（可选） | 日志、指标、告警 |

### 2.3 应用分层
- **接入层**：JWT + RBAC 鉴权、API 网关、参数校验；
- **应用层**：模板服务、任务服务、报告服务、比对服务；
- **领域层**：规则模型、任务状态机、操作留痕模型、版本模型；
- **基础设施层**：Mongo / ClickHouse / PostgreSQL / MinIO / Hangfire 适配器。

### 2.4 核心模块清单
| 模块 | 职责 |
|---|---|
| TemplateService | 模板管理、版本治理、启停、灰度发布 |
| TaskOrchestrator | 任务编排、状态推进、重试与幂等 |
| PreprocessEngine | 有效段计算、离群判定、质量标记、入仓 |
| AlgorithmEngine | DAG 算法编排执行（预留插件扩展） |
| CompareEngine | 同星跨批次、实测对基线/阈值比对 |
| ReportEngine | Word 模板渲染、文件入 MinIO |
| AuditService | 全链路操作与血缘记录 |
| IntegrationService | 第三方开放 API、异步任务、Webhook 投递 |

### 2.5 安全架构
- **身份认证**：JWT（Web 用户）、API Key/OAuth2（第三方）；
- **权限模型**：管理员、分析员、只读员（基于 RBAC）；
- **访问控制**：按角色 + 业务范围（卫星/批次）双重限定；
- **算法沙箱**：用户上传的 Python/JS 算法采用容器级隔离与资源限制；
- **留痕要求**：关键操作完整记录，不可篡改。

## 3. 业务架构

### 3.1 业务能力地图
- **资产配置中心**：
  - **海量数据接口服务地址**（HTTP）：从中拉取卫星列表、每颗卫星的参数列表，以及**每颗卫星对应的 MongoDB 连接地址**（不同卫星可能使用不同的 MongoDB 实例）；
  - **卫星资产地址**（HTTP）：从中拉取每颗卫星的测试时间段（测试批次）配置；
  - **内部数据源管理**：仅维护本平台自有的 ClickHouse 分析库、MinIO 对象存储、PostgreSQL 元数据库连接（**MongoDB 原始库地址不在此维护，由海量接口服务按卫星动态下发**）。
- **模板中心**：筛选模板、算法模板、报告模板
- **任务中心**：定时任务、手工补跑/重跑/回补、执行监控
- **数据处理中心**：预处理与质量标记、算法处理、一致性比对
- **报告中心**：报告生成、报告归档、报告查询与下载
- **治理中心**：灰度发布、操作留痕、运维告警
- **开放集成中心**：API 客户端凭据、异步任务与 Webhook 回调

### 3.2 关键业务流程

#### 流程 A：模板发布流程
1. 用户创建模板并保存为新版本；
2. 审核或直接启用；
3. 灰度规则生效（按卫星 / 批次 / 时间窗限定生效范围）。

#### 流程 B：预处理任务流程
1. 触发任务（定时或手工），指定目标卫星与批次；
2. 引擎从**海量数据接口服务**获取目标卫星的参数清单及其对应的 **MongoDB 连接地址**，从**卫星资产服务**获取该卫星的测试时间段配置，并解析模板规则；
3. 按动态返回的 MongoDB 地址连接到目标卫星的原始库，拉取对应参数与时间段的数据；
4. 计算有效时间段并提取目标参数；
5. 判定离群值并打标（不删除、不插值、不去重）；
6. 测点数值 Upsert 至 ClickHouse 高品质明细表，同步将任务血缘与规则写入 PostgreSQL 时间窗元数据表；
7. 写入任务留痕与血缘信息。

#### 流程 C：分析与报告流程
1. 算法引擎解析 React Flow 生成的 DAG 图，按节点执行模板（统计、频域、聚类、时序对齐等五阶算法）；
2. 执行一致性比对（多维基线比对、形态对齐等）；
3. 汇总结果，按报告模板生成 Word；
4. 入 MinIO 并回写索引，前端展示与下载。

#### 流程 D：第三方异步查询与回调
1. 第三方携带鉴权调用开放 API 创建异步任务（或查询已有 `run_id`）；
2. 系统立刻返回 `HTTP 202 Accepted` 及全局唯一 `jobId` / `runId`；
3. 第三方轮询 `GET /jobs/{id}` 直至终态，或注册 `callbackUrl` 接收 Webhook；
4. 任务终态（成功或失败）时，系统主动 `HTTP POST` 推送至 `callbackUrl`；
5. 投递可靠性：HMAC 签名防篡改，事件幂等键（eventId），退避重试，PostgreSQL `callback_deliveries` 留痕。

### 3.3 业务规则摘要
- **筛选规则**：AND/OR/NOT 逻辑，支持持续时长约束与边界缓冲；
- **数据质量**：不插值、不去重；
- **离群策略**：支持上下限阈值法、3σ/IQR/MAD 等统计法；支持全局或分段判定；
- **离群入库**：被标记数据不剔除，保留入库；
- **报告规范**：多模板可编辑，封面 / 章节 / 页码必需。

## 4. 核心功能模块设计

本章按"模块职责 — 关键能力 — 核心设计 — 输入/输出"四要素，对系统八大核心模块进行展开。模块间通过领域事件与状态机解耦，统一接入操作留痕与可观测体系。

### 4.1 模板治理模块（TemplateService）

**模块职责**：分别管理 **筛选模板**、**算法模板**、**报告模板** 三类模板的全生命周期。三类模板互相独立、无直接关联，由任务编排模块按需组合调用。

**关键能力**（三类模板共用）：
- 模板列表页：按类型独立展示，支持搜索、筛选、版本切换、状态过滤；
- 模板维护页：按类型独立提供编辑器，支持创建、编辑、克隆、版本对比（Diff）；
- 状态流转：草稿 → 待审核 → 已发布 → 灰度中 → 全量 → 归档；
- 灰度发布：按"卫星集 / 测试批次 / 时间窗口"三维度独立配置每类模板的生效范围。

**三类模板能力差异**：

| 模板类型 | 列表页关键列 | 维护页核心交互 | 核心字段 |
|---|---|---|---|
| **筛选模板** | 名称、版本、适用范围、状态、最近更新 | 规则条件树（AND/OR/NOT）、持续时长、边界缓冲 | `filter_template` 表 |
| **算法模板** | 名称、版本、节点数、状态、运行统计 | React Flow 画布拖拽编排（多阶段算法节点连线） | `algorithm_template` 表 |
| **报告模板** | 名称、版本、适用场景、状态、下载样例 | Word 模板上传 + 占位符变量映射、章节结构预览 | `report_template` 表 |

**核心设计**：
- **三类模板物理分表**：分别建 `filter_template`、`algorithm_template`、`report_template` 三张元数据表，互不关联，避免类型混淆与字段空置；
- **统一抽象服务接口**：三类模板共享同一抽象 `ITemplateProvider<TConfig>`，复用版本治理、状态机、灰度路由等通用逻辑；
- **前端独立菜单**：导航分别提供"筛选模板中心"、"算法模板中心"、"报告模板中心"三个一级入口，每个入口包含列表页 + 维护页；
- **版本不可变**：已发布版本只读；任何修改必须发布新版本；
- **灰度路由**：任务触发时由 `TemplateRouter` 按"模板类型 + 数据范围 + 时间窗"独立解析每类模板命中的版本，未命中灰度则使用稳态全量版本；
- **配置 JSON Schema 校验**：每类模板各自维护自己的 Schema，保障内容结构合法。

**输入/输出**：
- 输入：用户在三类模板维护页分别配置的内容；
- 输出：三类相互独立的模板版本快照，按需被任务编排引擎组合调用。

### 4.2 任务编排与调度模块（TaskOrchestrator）

**模块职责**：将业务请求编排为可执行任务，并管理整个生命周期。

**关键能力**：
- 定时触发（Cron）、手工触发、补跑（Backfill）、重跑（Rerun）；
- 任务依赖编排（预处理 → 算法 → 比对 → 报告）；
- 8 小时强制超时、失败重试、人工干预。

**核心设计**：
- **任务模型**：`run_id`（全局唯一）+ `job_type` + `parent_run_id`（用于子任务关联）；
- **状态机**：`Queued → Running → Succeeded / Failed / Timeout / Cancelled`；
- **幂等键**：`(模板版本, 卫星, 批次, 时间窗)` 哈希；同一幂等键重复提交不重复执行（除非显式声明 `force=true`）；
- **队列隔离**：基于 Hangfire 的多队列设计（`preprocess` / `algorithm` / `compare` / `report`）；
- **失败补偿**：可在 `task_run` 上发起精准窗口回补。

**输入/输出**：
- 输入：模板版本 + 数据范围 + 触发参数；
- 输出：任务运行实例 + 子任务链路。

### 4.3 预处理引擎（PreprocessEngine）

**模块职责**：将 MongoDB 原始数据按规则过滤并转换为 ClickHouse 高品质数据。

**关键能力**：
- 有效时间段计算（基于持续时长与边界缓冲）；
- 目标参数提取与对齐；
- 离群值判定与质量标记；
- 微批写入 ClickHouse + 元数据写入 PostgreSQL。

**核心设计**：
- **资产解析**：执行前由 `AssetService` 通过外部 HTTP 接口拉取目标卫星的参数列表与对应的 MongoDB 地址（来自海量数据接口服务）以及测试时间段配置（来自卫星资产服务）；
- **按星动态连接 MongoDB**：连接池按 `(tasook_no, satellite_no)` 维护多套 Mongo 客户端，地址变更时自动失效缓存重连；
- **离群判定算子**：插件式注册（阈值、3σ、IQR、MAD、Hampel），支持串/并联组合；
- **双态保留**：被判异常的数据 `is_outlier = 1` 仍入库，不物理删除、不插值、不去重；
- **微批写入**：按 10 万条/批批量 Insert，避免单条写入；
- **双写一致**：以 `run_id` 作事务边界，先写 ClickHouse 数值，后写 PostgreSQL 元数据；失败时通过 `run_id` 实现幂等回滚。

**输入/输出**：
- 输入：原始 Mongo 长表 + 筛选模板版本 + 时间窗；
- 输出：`hq_param_point`（数值）+ `hq_param_metadata`（血缘）。

### 4.4 算法引擎（AlgorithmEngine）

**模块职责**：执行 React Flow 编排的有向无环图（DAG），完成多阶段算法分析。

**关键能力**：
- 解析前端 React Flow JSON 拓扑；
- 节点级独立执行 + 节点间参数透传；
- 五阶算法体系全覆盖；
- 用户上传算法的沙箱化执行。

**核心设计**：
- **节点协议**：每个算法节点声明 `inputs / outputs / params / runtime`，引擎据此做静态校验与运行时调度；
- **执行模式**：拓扑排序后按层并行；同层多节点可分布式调度至不同 Worker；
- **五阶算法体系**：

| 阶段 | 算法 | 适用场景 |
|---|---|---|
| 一阶 稳态统计 | Max/Min/Mean/Var/RMS、阈值法、3σ | 稳态参数包络比对 |
| 二阶 频域 | FFT、PSD、主频/带宽提取 | 振动、微波等高频信号 |
| 三阶 时序对齐 | DTW、相关性分析 | 非稳态指令响应、瞬态打分 |
| 四阶 多维聚类 | K-Means、DBSCAN、PCA | 工况切分、伪标签、簇中心漂移 |
| 五阶 重构预测 | AE、LSTM 重构误差 | 高阶异常感知（依托外部 ML 平台） |

- **算法仓库**：用户上传的 Python/JS 脚本经审核后注册为节点；执行采用容器级隔离 + 资源限额；
- **结果落库**：原子结果写 `algo_result`，聚类标签写 `algo_cluster_labels`。

**输入/输出**：
- 输入：高品质明细 + DAG 编排 + 节点参数；
- 输出：算法指标、聚类标签、特征向量等中间产物。

### 4.5 比对引擎（CompareEngine）

**模块职责**：基于算法产物完成一致性判定。

**关键能力**：
- 同星跨批次比对、实测对基线比对、实测对阈值比对；
- 多维聚类比对（簇中心漂移、噪声率变化）；
- 时序形态比对（DTW 距离阈值）；
- 频域指标比对（主频偏移）。

**核心设计**：
- **比对算子可插拔**：每种比对模式实现统一接口 `Compare(InputA, InputB, Criteria) → Verdict`；
- **判定结论**：`正常 / 注意 / 异常`，并附详细维度分项打分；
- **基线管理**：基线版本与有效区间显式登记，避免基线漂移导致的误判；
- **结果归档**：写 `compare_result` 表，作为报告引擎的输入。

**输入/输出**：
- 输入：算法结果集 + 基线引用 + 比对模板；
- 输出：比对结论 + 详情 JSON。

### 4.6 报告引擎（ReportEngine）

**模块职责**：基于报告模板生成标准化 Word 文档。

**关键能力**：
- 多模板装配（封面、目录、章节、图表、附录、页码）；
- 数据回填（变量、表格、图片）；
- 渲染校验与异常兜底；
- 文件入 MinIO 并登记索引。

**核心设计**：
- **模板引擎**：基于 OpenXML 操作 .docx 占位符；
- **图表生成**：服务端渲染 SVG/PNG 后嵌入；
- **版本可追溯**：每份报告携带 `run_id + template_version + 生成时间`；
- **存储策略**：MinIO 启用版本控制，PostgreSQL `object_index` 维护索引。

**输入/输出**：
- 输入：比对结果 + 报告模板 + 元数据；
- 输出：Word 文件 + 文件索引记录。

### 4.7 资产配置中心（AssetService）

**模块职责**：统一对接外部资产源系统，向平台内部提供卫星、参数、测试时间段三类基础资产视图。本平台不在内部维护参数字典，全部以外部权威系统为准。

**关键能力**：
- 配置 **海量数据接口服务地址**（HTTP），用于获取卫星列表、每颗卫星的参数清单及对应 MongoDB 连接地址；
- 配置 **卫星资产服务地址**（HTTP），用于获取每颗卫星的测试时间段（测试批次）配置；
- 配置内部数据源（ClickHouse / MinIO / PostgreSQL 等本平台自有存储）连接信息；
- **不再维护 MongoDB 原始库地址**：每颗卫星的 MongoDB 地址由海量接口服务按卫星动态下发；
- 拉取后的资产视图本地缓存与定期刷新；
- 接口连通性检测、鉴权信息管理、错误告警。

**核心设计**：
- **两个外部服务 + 适配器**：

  | 配置项 | 协议 | 返回内容 | 调用场景 |
  |---|---|---|---|
  | 海量数据接口服务地址 | HTTPS / REST | 卫星列表（`tasook_no, satellite_no, name, type` 等，`tasook_no + satellite_no` 唯一确定一颗卫星）；指定卫星的参数列表（`param_id, name, unit, range` 等）；**该卫星对应的 MongoDB 连接信息**（`mongo_uri, db_name, auth_ref` 等） | 模板配置下拉选取、任务执行时确定参数清单与原始库地址 |
  | 卫星资产服务地址 | HTTPS / REST | 指定卫星的测试时间段（`test_batch_id, start_ts, end_ts, scenario` 等） | 任务调度时确定有效时间窗 |

- **配置模型**（PostgreSQL `data_source_config` 表）：
  - `source_type`：枚举（`MASS_DATA_API` / `SATELLITE_ASSET_API` / `CLICKHOUSE` / `MINIO` / `PG_META`）；**不含 `MONGO` 类型**；
  - `endpoint_url`、`auth_type`、`auth_secret_ref`（密钥引用）、`timeout_ms`、`enabled`；
  - 支持每种类型多套环境（开发/测试/生产）切换。
- **MongoDB 按星动态连接**：
  - 每次任务执行时由海量接口返回当前卫星的 Mongo 地址；
  - 平台内置 `MongoConnectionPool`，以 `(tasook_no, satellite_no)` 为 key 缓存连接，地址变更时自动作废重建；
  - 鉴权信息可通过密钥引用从外部密钥管理系统获取，避免落库明文。
- **本地缓存与刷新**：
  - 卫星列表、参数列表、Mongo 地址映射入 PostgreSQL 缓存表（`satellite_cache` / `param_cache`），带版本号与 `last_synced_at`；
  - 支持手工刷新、定时刷新（默认每日）、任务触发时按需刷新；
  - 缓存命中失败时回退实时调用并补缓存，保障外部服务抖动下的可用性。
- **统一适配层**：以 `IAssetProvider` 接口对接，未来可扩展第三种或第四种外部资产源系统。

**输入/输出**：
- 输入：管理员配置的 HTTP 地址 + 鉴权凭据；
- 输出：可被模板服务、任务编排、预处理引擎调用的卫星/参数/时间段视图。

### 4.8 用户、操作留痕与开放集成模块

**模块职责**：保障平台的安全、可追溯、可被第三方集成。

**关键能力**：
- **用户与权限（IdentityService）**：JWT 登录、RBAC（管理员 / 分析员 / 只读员）、按业务范围（卫星/批次）二级控权；
- **操作留痕（AuditService）**：模板发布、任务触发、数据导出、配置变更等关键操作全程记录，记录前/后值；
- **开放集成（IntegrationService）**：异步任务 API、状态轮询、Webhook 回调（HMAC 签名 + eventId 幂等 + 退避重试 + 投递留痕）。

**核心设计**：
- **统一拦截**：所有写操作经 AOP 切面写 `audit_log`（操作留痕表）；
- **API Key 仅存哈希**：明文一次性返回，不可二次查看；
- **Webhook 投递独立队列**：避免业务任务影响回调时效；
- **客户端态视图**：在操作留痕与开放 API 页面集中展示客户端、回调记录、失败重试。

**输入/输出**：
- 输入：用户操作 + 第三方调用 + 任务终态事件；
- 输出：操作留痕日志 + API 响应 + Webhook 投递记录。

## 5. 数据架构

### 5.1 数据分层
| 层级 | 存储 | 内容 |
|---|---|---|
| ODS（原始层） | MongoDB | 原始长表参数数据 |
| DWD（明细层） | ClickHouse | 过滤后参数明细 + 质量标记 |
| DWS（汇总层） | ClickHouse | 算法结果、比对结果 |
| META（元数据层） | PostgreSQL | 模板、版本、任务、操作留痕、血缘 |
| FILE（对象层） | MinIO/S3 | 报告文件、算法包、导出附件 |

### 5.2 核心数据实体

#### ClickHouse（高吞吐分析层）
- **`hq_param_point`（高品质明细表）**：
  - 业务联合主键：`tasook_no, satellite_no, test_batch_id, param_id, ts`（其中 `tasook_no + satellite_no` 唯一确定一颗卫星）；
  - 数值状态：`raw_value, processed_value, is_outlier`；
  - **极简结构**：取消行级 `run_id` 和模板信息；
  - **覆盖语义**：同一 `(tasook_no, satellite_no, test_batch_id, param_id, ts)` 仅保留最新一份（`ReplacingMergeTree` 实现 Upsert）。
- **`algo_result`（算法结果表）**：`run_id, template_version, metric_name, metric_value, window_start, window_end`；聚类算法可额外记录簇分布特征、簇中心漂移（Centroid Drift）。
- **`algo_cluster_labels`（聚类标签表）**：`tasook_no, satellite_no, test_batch_id, ts, cluster_id`；记录每个样本的伪标签与孤立点标记，避免修改海量明细表。
- **`compare_result`（比对结果表）**：`compare_run_id, compare_type, baseline_ref, score, decision, detail_json`。

#### PostgreSQL（元数据与血缘层）
- **`hq_param_metadata`（时间窗元数据表）**：
  - `tasook_no, satellite_no, test_batch_id, param_id, window_start, window_end`；
  - `run_id, template_version, outlier_method, outlier_reason_pattern`；
  - 承接从明细表中剥离的冗余溯源信息；前端或下游通过时间窗反查血缘。
- **`filter_template` / `algorithm_template` / `report_template`**：三类模板分表存储，结构相似（`template_id, version, status, gray_scope, config_json, created_by, updated_at`）但互相独立，不通过外键直接关联；
- **`task_run`**：`run_id, job_type, trigger_type, status, start_time, end_time, timeout_flag, error_msg`；
- **`data_source_config`**：`source_id, source_type, endpoint_url, auth_type, auth_secret_ref, timeout_ms, enabled`；登记两个外部 HTTP 服务（海量数据接口、卫星资产服务）及内部存储连接；
- **`satellite_cache` / `param_cache`**：本地缓存外部接口拉取的卫星与参数清单，含 `last_synced_at` 与版本号；
- **`audit_log`**：`operator, action, target_id, before_json, after_json, action_time`；
- **`object_index`**：`object_id, bucket, object_key, version, checksum, content_type, ref_run_id`；
- **`api_clients` / `client_callbacks` / `callback_deliveries`**：第三方客户端、回调 URL、签名密钥版本、Webhook 投递记录。

> 详细 PostgreSQL 表级展开见《PostgreSQL 元数据与对外接口设计说明 V1.0》。

### 5.3 关键存储设计决策

#### 决策一：高品质明细单表 + 物理分区（替代一星一表）
针对 100 颗卫星 × 1.5 万参数的庞大数据量：
- 采用 **"单张大表 + `PARTITION BY (toYYYYMM(ts), tasook_no, satellite_no)`"**（按"型号代号 + 卫星代号"做物理分区）；
- 既享受跨星联合分析（如多维聚类）的简洁性，又获得"一星一表"级别的物理隔离查询性能；
- 简化数据归档（直接 `DROP PARTITION`），规避元数据灾难。

#### 决策二：极简明细 + 元数据剥离
明细表只保留数值与轻量标记，将冗长的模板版本与离群原因抽离到 PostgreSQL 时间窗元数据表中。
- 利用 ClickHouse 列式压缩特性，明细表磁盘占用极低；
- 业务模板变更（如改文案）不影响海量底层数据；
- 第三方消费时直接读取明细，无需带 `run_id`，需要血缘时通过时间窗反查。

#### 决策三：资产数据外部权威 + 本地缓存
卫星列表、参数清单、**MongoDB 原始库地址**、测试时间段不在平台内部维护静态字典，统一由外部 HTTP 服务（海量数据接口服务、卫星资产服务）作为权威数据源：
- 平台仅保留 **两个外部 HTTP 服务地址** 与鉴权配置，避免双源不一致；
- **MongoDB 地址按星动态下发**：每颗卫星可使用不同的 MongoDB 实例，预处理引擎通过连接池按 `(tasook_no, satellite_no)` 动态切换；
- 本地缓存提升查询性能并兜底外部抖动；
- 当外部资产体系发生硬件/编号/原始库迁移时，平台无需人工同步映射。

### 5.4 数据血缘与可追溯
每条结果可追溯至：来源任务 `run_id`、模板版本 `template_version`、输入数据时间窗、**数据来源**（`tasook_no + satellite_no`，唯一确定一颗卫星）、所属测试时间段 `test_batch_id`、输出文件 `object_id`。

### 5.5 数据保留与归档
- 高品质明细按月分区，历史冷数据可下沉归档（基于 ClickHouse 存储策略）；
- 操作留痕数据长期保留；
- MinIO 开启版本控制与生命周期策略。

### 5.6 机器学习扩展
- ClickHouse 高品质点表作为**时序事实**；
- 训练样本（`[T,C]` 张量、变长序列）在 **ML 数据集快照层** 显式定义并版本化；
- 缺失数据采用 **padding + mask** 表达，与"不插值"约束一致；
- 数据集划分按时间或批次隔离，避免序列泄漏；
- 数据集快照 ID、`run_id` 集合、通道映射、归一化参数文件登记于 PostgreSQL，归一化参数文件可存 MinIO。

## 6. 接口与开放集成设计

### 6.1 异步长任务机制
预处理与比对任务受 8 小时强制中断策略限制，对外采用异步解耦：
- `POST /api/v1/jobs/preprocess` → 立即返回 `HTTP 202 Accepted` + `jobId/runId`；
- 第三方通过 `GET /api/v1/jobs/{id}` 轮询查询状态。

### 6.2 Webhook 回调机制
- 第三方注册 `callbackUrl`，任务终态时系统主动 `HTTP POST` 推送结果或下载链接；
- **HMAC 签名** 防篡改、**eventId 幂等键** 防重复消费；
- 失败按指数退避重试，所有投递记录写入 PostgreSQL `callback_deliveries` 表留痕。

### 6.3 鉴权与限流
- API Key（仅存哈希）或 OAuth2 Client Credentials；
- 可结合 IP 白名单；
- 限流、错误码、请求追踪 ID 见专项设计文档。

## 7. 部署架构

### 7.1 部署拓扑（逻辑）
- **接入区**：Web 前端、API 服务（多实例）；
- **计算区**：Hangfire Server、预处理 Worker、算法 Worker、比对 Worker、报告 Worker（按队列隔离）；
- **数据区**：MongoDB、ClickHouse、PostgreSQL、MinIO、Redis（可选）。

### 7.2 环境规划
| 环境 | 部署形态 | 用途 |
|---|---|---|
| DEV | 单机或轻量多容器 | 开发自测 |
| SIT/UAT | 接近生产 | 联调与性能验证 |
| PROD | 多实例高可用 | 生产运行，含数据备份与监控 |

### 7.3 高可用与容灾
- API 与 Worker 多副本部署；
- 任务队列与数据库定期备份；
- ClickHouse 与 MinIO 具备冗余策略；
- 关键配置与模板版本异地备份。

### 7.4 运维监控
- **监控维度**：任务成功率/失败率/超时率、队列积压长度、Mongo 查询时延、ClickHouse 写入/查询耗时、报告生成耗时；
- **告警规则**：连续失败任务、超时任务、回补积压、存储容量阈值。

### 7.5 容器化部署建议
- 核心管理 API 与 Hangfire 调度主节点高可用部署；
- 后台 Worker 按计算密集度隔离队列（preprocess / algorithm / compare / report）；
- ClickHouse 搭配 ZooKeeper 集群化；MinIO 开启多盘纠删码与版本控制。

## 8. 非功能设计

### 8.1 性能
- **批量写入**：MongoDB 到 ClickHouse 必须采用微批处理（10 万条/批），严禁单条 Insert；
- **任务并发**：可配置上限，避免资源争抢；
- **长任务分片**：降低单任务失败影响面。

### 8.2 可靠性
- **任务幂等**：基于 `(模板版本, 时间窗, 卫星, 批次)` 生成幂等键；
- **失败重试**：自动重试 + 人工重跑；
- **精确回补**：可按窗口重算。

### 8.3 可维护性
- 模块边界清晰，配置集中管理；
- 关键流程具备操作留痕与可观测信息。

### 8.4 安全性
- RBAC 权限控制；
- 重要数据最小权限访问；
- 上传代码执行隔离与留痕。

## 9. 分阶段实施建议

### 一期（当前）
- 打通业务闭环：模板 → 预处理 → 算法 → 比对 → 报告；
- 完成任务治理与操作可追溯；
- 上线基础运维能力；
- 算法落地聚焦**第一阶段（基础统计）+ 第二阶段（频域 FFT）**。

### 二期（演进）
- 增强可视化编排（复杂分支/循环/并行）；
- 完善插件化算法运行时（用户上传 Python/JS 沙箱）；
- 落地**第三阶段（DTW 时序对齐）+ 第四阶段（聚类基线）**；
- 增加 ML 数据集版本化与特征工厂能力。

### 三期（智能化）
- 对接外部 ML 平台，落地**第五阶段（AE 重构误差比对）**；
- 全量开放 HTTPS REST + Webhook 集成；
- 构建跨星组网级一致性比对大屏。
