# 卫星测试数据预处理与数据分析平台
## 需求分析说明文档（V1.1）

## 1. 文档目的
本文档用于明确“卫星测试数据预处理与数据分析平台”的业务目标、功能范围、核心流程、数据要求及非功能要求，作为后续系统设计、开发实施与验收依据。

## 2. 项目背景与目标
卫星测试阶段产生大量历史参数数据，现需建设统一平台实现：
- 从原始库提取历史测试数据并形成高品质数据层；
- 基于模板化规则进行数据筛选、处理与一致性比对；
- 输出标准化报告文档；
- 支撑后续机器学习/深度学习使用的数据生产与治理。

## 3. 业务范围
### 3.1 包含范围
- 原始数据查询、筛选、过滤、标记、入仓；
- 算法编排与执行；
- 一致性比对与报告生成；
- 模板管理（筛选模板、算法模板、报告模板）；
- 任务调度、补跑、重跑、回补；
- Web 管理与可视化配置。

### 3.2 非范围（当前阶段）
- 实时闭环控制；
- 自动控制类决策下发；
- 外部模型服务部署（仅预留接口能力）。

### 3.3 对外集成（演进需求）
- 允许经授权的**第三方系统**通过 **HTTPS** 调用开放接口，获取预处理与算法结果（任务时间窗、统计量、包络线等）；
- 长时任务采用**异步**模式，处理完成后通过 **Webhook 回调**通知第三方，并配套**轮询查询**作为兜底（详见《PostgreSQL元数据与对外接口设计说明》）。

## 4. 术语定义
- **原始数据**：MongoDB 长表结构测试数据（统一时间基准），含数据值、单位、描述等。
- **高品质数据**：按筛选模板与质量规则处理后存入 ClickHouse 的数据。
- **筛选模板**：先计算有效时间段，再提取目标参数的规则模板。
- **算法模板**：由多个算法节点组成的可编排流程模板。
- **一致性比对**：同一卫星不同测试批次、实测 vs 基线/阈值的对比分析。
- **回补**：晚到数据入库后对目标窗口执行补算。
- **业务任务批次（run_id）**：一次预处理/算法等流水线实例的唯一标识；算法结果应对齐到 `run_id`，而**高品质明细数据全局唯一，仅包含测点值和轻量异常标记，溯源信息按时间窗和参数提取到元数据表中**。

## 5. 业务需求说明

### 5.1 数据筛选与模板化
系统应支持制定参数筛选策略并形成模板，要求：
- **参数字典与逻辑别名映射**：模板配置时必须使用参数的逻辑别名（Alias）进行抽象定义，平台在任务执行时根据卫星型号的参数字典动态解析为底层物理 ID，以支撑**跨星组网的模板复用**并规避底层硬件物理 ID 变更对模板的影响；
- 支持多参数组合逻辑：`AND/OR/NOT`；
- 支持“先条件参数求有效时间段，再在该段内查询目标参数”；
- 支持持续时长条件（连续满足 N 秒）；
- 支持边界缓冲（有效段前后扩展）；
- 模板支持版本管理、启停、灰度发布。

### 5.2 数据抽取与高品质层构建
系统应支持根据多个筛选模板，定期从 MongoDB 查询历史数据并过滤后写入 ClickHouse：
- 支持定时任务；
- 支持手工补跑/重跑；
- 支持晚到数据回补；
- 支持任务运行日志、状态跟踪与失败告警。

### 5.3 高品质数据质量规则
- 高品质数据为符合筛选条件的数据；
- 支持离群值判定与标记；
- **不进行插值、不进行去重**；
- 被判定为离群值的数据**仍需入库**并标记，不可删除。

### 5.4 离群值判定能力
离群值规则由用户可配置，支持：
- 业务阈值法（用户指定上下限）；
- 常用统计法（如 3σ、IQR、MAD 等）；
- 判定粒度支持：
  - 全局判定；
  - 按工况段/时间段分段判定；
- 参数级配置：不同参数可采用不同判定方法和粒度。

### 5.5 算法处理与一致性比对的演进路线
系统需对高品质数据进行多种处理与比对，为保障可落地性，算法能力按以下阶段逐步建设：

#### 第一阶段：基础打底（稳态与规则比对）
- **统计与包络算法**：最大值、最小值、均值、方差、标准差、RMS；
- **比对作用**：实测数值对设计阈值（上下限）的硬约束检查，以及基于 3-Sigma 等经典统计学的主流离群值判定。

#### 第二阶段：频域扩展（高速信号比对）
- **信号处理算法**：FFT（快速傅里叶变换）、PSD（功率谱密度）、频域特征提取；
- **比对作用**：针对微波、振动、动量轮转速等高频数据，将实测时域信号转为频域后，比对特定频率下的峰值与能量带分布一致性（发现装配异音或高频干涉）。

#### 第三阶段：时序形态对齐（瞬态过程比对）
- **时序匹配算法**：DTW（动态时间规整）、相关系数分析；
- **比对作用**：针对有明确起点终点的指令响应与瞬态过程（如帆板展开、开机上电序列），允许时间轴上存在微小拉伸缩短的弹性对齐，进行“波形走势”的一致性打分。

#### 第四阶段：多维基线与聚类（多变量联动比对）
- **无监督学习（聚类降维）**：K-Means、DBSCAN、PCA 主成分分析；
- **比对作用**：通过聚类自动切分隐藏工况段、生成伪标签。利用历史多维数据降维后形成的“高密度包络簇”作为多维基线，检验新批次数据的“系统级联动一致性”，捕捉多维微小退化（簇中心漂移）。

#### 第五阶段：高阶重构与预测（深度学习比对）
- **深度学习模型**：自编码器（AE）、LSTM 等（依托外部 ML 平台）；
- **比对作用**：利用平台积累的高品质历史基线数据训练 AE 模型。用实测数据进行重构预测，输出“重构误差”作为一致性得分，专门用于发现隐含的元器件性能微降与非线性耦合偏移。

*注：当前平台核心功能建设聚焦于第一、二阶段，三至五阶段以算法扩展和对接外部 ML 平台的形式逐步落地。*

### 5.5.1 算法可扩展性要求
- 算法模板支持多节点编排；
- 支持用户上传 Python 或 JavaScript 算法扩展；
- 算法节点之间支持参数透传与连线校验。

### 5.6 编排能力（流程图式）
算法模板编排需支持：
- 条件分支；
- 循环；
- 并行节点；
- 节点参数配置与透传；
- 节点输入输出约束与连线合法性校验；
- **拖拽式交互**：体验借鉴 Dify、Coze 等大模型工作流编排平台（左侧组件库、中间连线画布、右侧参数配置面板），前端技术选型**采用 React Flow 框架实现**。

### 5.7 一致性比对与输出
一致性比对应用上述算法，具体包含以下维度：
- 同一卫星不同测试批次比对；
- 实测 vs 基线/指标阈值比对；
- **时序波形对齐**：对于非稳态测试或指令响应动作，通过 DTW 等算法进行瞬态形态打分；
- **多维聚类比对**：基于历史数据聚类形成的高维基线，检验新测试批次的多参联动一致性与簇中心漂移量；
- **高阶重构对齐**：引入预训练的深度学习重构误差来评估复杂非线性的联动一致性破缺；
- 比对结果输出为报告文档。

### 5.8 报告管理
- 最终报告格式：**Word（.docx）**；
- 支持多个报告模板；
- 报告模板可编辑；
- 报告必需元素：封面、章节、页码；
- 报告应包含任务信息、数据范围、方法、结果、异常明细、结论等核心内容。

### 5.9 UI 与角色权限
角色：
- 管理员；
- 分析员；
- 只读员。

核心页面：
- 任务监控；
- 模板管理（筛选模板/算法模板/报告模板）；
- 算法仓库；
- 比对报告；
- 品质数据与标记（预处理后明细与质量标记，见原型与详细设计）。

### 5.10 第三方开放接口（HTTPS / REST）
- 对外协议优先采用 **HTTPS + REST + JSON**，配套 **OpenAPI** 规范文档；
- 提供资源型接口，包括但不限于：
  - 任务/运行元数据（时间窗、卫星、测试批次、状态、模板版本）；
  - 算法结果（最大值、最小值、均值、方差、标准差、包络线等；大包络线可返回对象存储下载地址）；
- **异步长任务**：
  - 提交后返回 **HTTP 202** 及 `jobId`/`runId`；
  - 第三方可通过 **轮询** `GET .../jobs/{id}` 查询状态与结果摘要；
  - 处理完成后，本系统向第三方登记的 **callbackUrl** 发起 **Webhook（HTTP POST）** 投递完成/失败事件；支持签名（如 HMAC）、重试与投递审计；
- 鉴权：OAuth2 Client Credentials、**API Key**（仅存哈希）或等效机制；可结合 IP 白名单；
- 限流、错误码、请求追踪 ID 等见专项设计文档。

### 5.11 高品质数据主键语义（轻量化设计）
- 若同一 `(卫星, 测试批次, 参数, 时间戳)` 被预处理，在 ClickHouse 中**仅保留一份**，业务唯一键为 `(卫星, 测试批次, 参数, 时间戳)`；
- 预处理后的 ClickHouse 数据行不再存储冗长的模板及原因，仅保留测点原始值、处理值及轻量化离群标记；
- **任务溯源与规则血缘**：抽取到轻量级的**时间段元数据表**（基于 PostgreSQL），按 `(参数, 时间窗)` 记录最后处理它的 `run_id`、模板版本及判定方法，前端或第三方可通过时间窗关联获取上下文；
- 与「不插值、不去重」的关系：不在源侧合并重复测点，但对于同一参数的同一时段，若有新的预处理任务（如不同的模板或重跑），后执行的任务将**覆盖或更新（Upsert）**该时段的高品质数据及元数据；
- 下游机器学习或第三方消费时，直接读取该参数的高品质明细数据即可，无需在查询时限定 `run_id`。

## 6. 关键规则（治理要求）
1. **全链路可追溯**  
   每条结果可追到模板版本、算法版本、报告模板版本、运行批次、输入时间窗、数据来源。
2. **幂等与覆盖重算**  
   同一任务同一输入结果一致；支持补跑、重跑、回补；多次预处理覆盖同一时间段的同一参数时，**高品质层数据将被最新任务的结果覆盖**（Upsert 语义）。
3. **高品质数据双态保留**  
   保留原始值与处理值，并记录离群标记与原因。
4. **模板灰度发布**  
   支持按卫星、按测试批次、按时间窗灰度发布。
5. **执行控制**  
   单次任务执行超时上限：**8小时**；超时需中断并记录原因。

## 7. 数据与处理流程（逻辑）
1. 从 MongoDB 按模板条件查询原始长表数据；
2. 计算有效时间段（逻辑条件 + 持续时长 + 边界缓冲）；
3. 在有效时间段内提取目标参数；
4. 执行离群值判定并打标（不删除、不插值、不去重）；
5. 测点数值写入 ClickHouse 高品质明细表（Upsert），同步将任务血缘与规则写入 PostgreSQL 时间窗元数据表；
6. 运行算法模板生成统计/特征结果；
7. 执行一致性比对（包含统计比对、频域比对、时序对齐、聚类基线比对等）；
8. 按报告模板生成 Word 报告；
9. 保存任务审计与版本追踪信息。

## 8. 机器学习/深度学习扩展要求（新增）
为支持后续 ML/DL，预处理体系需补充：

### 8.1 数据集版本化与可复现
- 训练数据集需具备数据集ID与快照能力；
- 记录数据来源、模板版本、算法版本、时间窗口；
- 同版本可重复产出一致数据。

### 8.2 标签与样本管理
- 支持样本窗口定义（按时间/事件）；
- 支持标签版本与变更审计；
- 支持训练/验证/测试集划分策略留痕。

### 8.3 防数据泄漏
- 数据切分应按时间或测试批次隔离；
- 禁止使用未来信息构造当前时刻特征；
- 明确可用于训练/不可用于训练字段集。

### 8.4 训练-推理一致性
- 标准化参数（如 mean/std）需固化并复用；
- 缺失/离群策略在训练与推理阶段保持一致；
- 维持“不插值、不去重”约束一致性。

### 8.5 ML数据质量门禁
- 增加标签覆盖率、类别分布、异常比例等指标；
- 设置训练前质量检查与阻断规则。

### 8.6 序列 / 深度学习补充（相对表格 ML）
- ClickHouse 高品质点表作为**时序事实**；训练用 **样本**（如 `[T,C]` 张量、变长序列）应在 **ML 样本层或导出快照**中显式定义，并版本化；
- 多参数对应 **多通道**，需固定 **通道顺序**（param_id → channel 映射）及 **归一化参数文件**版本，保证训练/推理一致；
- 变长序列采用 **padding + mask** 等策略时，与「不插值」协调：**缺失用 mask 表达**，不在 HQ 层插值补点；
- 划分 train/val/test 时优先按 **时间**或 **测试批次**，避免序列泄漏；详见总体设计文档数据与 ML 章节。

### 8.7 聚类算法支持（无监督学习）
- **功能定位**：通过对多维时序参数进行聚类（如 K-Means、DBSCAN 等），自动发现测试数据中的隐藏工况段、构建多维基线包络、发现新型/未知异常，并为海量无标注数据生成伪标签。
- **输入输出要求**：
  - **输入**：高品质明细数据层透视后的参数矩阵（张量）以及相关超参数（K值、eps、归一化策略等）。
  - **输出 (样本级)**：各个样本时间点的簇标签（Cluster ID）与异常噪声标记，关联写入数据库。
  - **输出 (统计与基线级)**：计算簇漂移（Centroid Drift）、簇分布占比用于一致性评估；支持生成聚类模型对象并持久化（MinIO）以供其他批次比对调用。

## 9. 非功能需求
- 可用性：任务失败可重试，支持断点续跑（按实现方案细化）；
- 可维护性：模板、算法、报告支持版本管理；
- 可审计性：关键操作与结果可追踪；
- 安全性：用户上传代码需隔离执行与权限控制；
- 性能约束：单次任务超时上限 8 小时（可按任务类型扩展配置）。

## 10. 技术架构与存储分层要求（新增）
### 10.1 后端技术路线
- 后端采用 **C#/.NET** 技术栈（推荐 .NET 8 LTS）；
- 支持 REST API、角色权限控制、模板治理、任务编排与审计追踪。

### 10.2 任务调度组件（Hangfire）职责
- 采用 **Hangfire** 作为统一任务调度与运维监控组件；
- Hangfire 负责：定时触发、手工触发、重试、失败记录、任务可视化监控；
- Hangfire 不直接承载重计算核心逻辑，重计算在独立处理模块/Worker中执行；
- 需支持补跑、重跑、回补，并与任务审计链路打通；
- 单次任务执行超时 8 小时，超时自动中断并记录原因。

### 10.3 对象存储要求（MinIO/S3）
- 引入对象存储，用于保存非结构化产物；
- 默认采用 **MinIO**，并要求兼容 S3 协议替代品；
- 存储对象至少包括：Word 报告文件、用户上传算法包、导出结果、审计附件；
- 数据库中仅存对象元数据与访问索引（如 bucket、object_key、version、checksum）。

### 10.4 数据分层职责
- **MongoDB**：原始长表数据源；
- **ClickHouse**：高品质数据、算法处理结果、一致性比对结果。其中**高品质明细数据强烈建议采用“单张大表 + 物理分区（按月份与卫星ID联合分区）”设计**，以保障跨星联合比对（如聚类算法）的性能，避免“一星一表”带来的元数据灾难与联合查询瓶颈；
- **关系型数据库（建议 PostgreSQL）**：模板元数据、版本信息、任务状态、**第三方客户端与回调投递**、对象索引、审计日志等（详见《PostgreSQL元数据与对外接口设计说明》）；
- **MinIO/S3**：报告与算法包等文件对象。

### 10.5 存储抽象与可替换性
- 系统需定义统一对象存储接口，屏蔽 MinIO 与其他 S3 实现差异；
- 通过配置切换对象存储实现，不影响业务层功能逻辑。

## 11. 验收要点（建议）
1. 可创建并发布筛选模板，支持逻辑条件、持续时长、边界缓冲；
2. 可按模板定期从 MongoDB 抽取并写入 ClickHouse；
3. 离群值可按多种方法判定，且被标记数据可入库；
4. 不发生插值和去重行为；
5. 算法编排支持基于可视化连线（工作流模式）的拖拽式交互，支持分支、循环、并行与参数透传；
6. 算法处理能够分阶段执行验证，涵盖基础统计、频域处理（如 FFT）及聚类分析（多维包络与工况切分）；
7. 可完成同星跨批次与实测对基线/阈值的一致性比对（包含静态阈值与时序形态对齐）；
8. 可基于多报告模板输出 Word，包含封面、章节、页码；
9. 支持补跑/重跑/回补；
10. 支持按卫星、测试批次、时间窗灰度发布；
11. 审计信息完整可查；
12. Hangfire 任务支持可视化监控、失败重试、超时中断；
13. 报告与算法包可存储在 MinIO（或 S3 兼容替代）并可追溯检索；
14. 高品质明细全局唯一且极简化，无冗长行级描述；任务血缘与规则由按时间窗和参数维度的元数据表承载；
15. （若实施开放接口）提供 HTTPS REST 异步任务 + 轮询 + Webhook 回调能力，并有投递审计。
